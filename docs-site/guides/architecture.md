How the compiler is put together, and why each seam is where it is.

## Four layers

Strictly one-directional. Later layers import earlier ones and never the reverse.

```
  spec files  ──parse──▶  IR  ──emit──▶  engine artifacts  ──prepare──▶  platform files
      ▲                    │                   │
      │                    │                   │
      └────import──────────┘                   └── diagnostics carry spec locations
        (engine → spec)                            back to the authored file
```

| Layer | Package | Job |
|---|---|---|
| **Spec** | `agentbridge.spec` | The authored artifact, in and out |
| **IR** | `agentbridge.ir` | Engine-neutral models. The contract |
| **Backends** | `agentbridge.backends` | One module per engine behind `RuntimeBackend` |
| **Deployment** | `agentbridge.deploy` | One module per platform behind `DeploymentTarget` |

The rule is enforced by tests, not convention: `test_ir_neutrality.py` parses the IR's AST and
fails if it imports from `backends` or `deploy`.

## The IR names no engine

If a field exists only because LangGraph has typed graph state, it isn't a contract — it's
LangGraph's shape wearing a neutral name, and the third engine will need the IR *edited*
rather than extended.

The test strips comments and string literals from `ir/` and `spec/`, then greps the remaining
code for `langgraph`, `langchain`, `crewai`, `claude_code`, `.claude`. Prose may explain the
rule; code may not break it.

Practical consequence: **if adding a backend makes you want to add an IR field, stop.** That's
the signal an engine assumption is leaking into the contract.

## Deployment is a separate ABC

`RuntimeBackend` and `DeploymentTarget` are deliberately not merged. Platforms are different
products from runtimes; an engine can run locally with no target at all; one engine may have
several. See [Deploying](doc:deploying).

## Engines are plugins

`BackendRegistry` and `DeploymentRegistry` hold built-ins plus anything advertised under the
`agentbridge.backends` / `agentbridge.deploy` entry-point groups. Adding an engine means adding
a module and an entry point — never editing the parser or the IR.

## Conformance testing

"Same spec, both engines" is only real if something checks it. The suite asserts on
**observable behaviour**, not generated bytes.

Each backend implements:

```python
def contract(self, bundle: Bundle, files: list[EmittedFile]) -> EngineContract: ...
```

reporting which agents, skills, tools, and nodes it actually materialised — **derived by
inspecting its own output**, not by copying the input bundle. A contract read off the input
could not catch a backend that silently skipped something, which is the entire point.

That requires the output to be introspectable. LangGraph output is Python, so the contract
greps for symbols it emitted. Claude Code output is Markdown, so the emitter leaves
machine-readable HTML-comment trailers in each agent file:

```html
<!-- agentbridge:tools read-file=Read,web-search= -->
<!-- agentbridge:skills citation-format -->
```

These pay for themselves twice. Frontmatter must name tools the way the *engine* does
(`Read`), but the IR uses the spec's name (`read-file`) — the trailer records the pairing, so
`import` lands back on the spec it came from instead of a slugified approximation. It also
carries the agent→skill association, which the plugin format has nowhere else to put.

The suite is parametrised over `registry.names()`, so a new engine inherits it by existing. It
checks that every backend:

- emits without errors
- materialises every agent, skill, tool, and node
- agrees with every other backend
- emits syntactically valid Python
- keeps emitted paths relative and contained
- **produces a diagnostic for every lossy row it declares in the mapping table**

## Running the generated program

Beyond structure, the suite writes the generated LangGraph program to disk, imports it, builds
the real graph, and invokes it — covering both branch paths. Enough sources on the first pass
goes straight to the writer; no sources loops until the round cap stops it.

No API key is needed, because `build_graph()` takes an injectable `model_factory`. That seam
isn't a testing afterthought — it's also how you change provider or route agents to different
models.

## Two round trips

They check different things:

| Round trip | What a failure means |
|---|---|
| `spec → IR → spec → IR` | A bug in the **spec format** — it goes through no engine |
| `spec → plugin → IR` | Agents, skills, prompts, capabilities preserved. Control flow lost **by design**, with `BRIDGE300` pointing forward at the consequence |

## What the LangGraph backend generates

```
workflow/
  state.py      TypedDict with Annotated reducers
  tools.py      imported callables and builtin shims
  skills.py     each skill as a load-on-demand tool
  agents.py     one node factory per agent, plus the model factory
  graph.py      StateGraph assembly and build_graph()
```

Three details that are decisions, not accidents:

**`build_graph(config=None, *, checkpointer=None, model_factory=None)`.** `config` is accepted
and ignored so the function doubles as a Platform graph factory — the manifest points at it
rather than a module-level graph, so importing doesn't require credentials.

**Builtin tools get real implementations.** Without `agentbridge.runtime.builtins`, a spec that
reads a file would compile on both engines but only *run* on one — making "same workflow, two
runtimes" true only on paper.

**The prebuilt-agent API is version-shimmed.** LangGraph 1.0 moved `create_react_agent` to
`langchain.agents.create_agent` *and* renamed its prompt keyword, so the import path alone
can't distinguish them. Generated `agents.py` carries a `_build_agent` helper handling both;
both paths are covered by tests.

## Toolchain

```bash
python -m pytest                                   # all tests
python -m pytest tests/test_conformance.py -k skill    # one test
python -m pytest -k "not GeneratedProgramRuns"     # skip tests needing langgraph
mypy                                               # strict
ruff check src tests && ruff format src tests
```

The compiler depends on `pydantic` and `PyYAML` and nothing else — it can emit a LangGraph
program on a machine with no LangGraph installed. Tests that build and invoke the generated
graph `importorskip` when it's absent.

## Known limits

- **CrewAI is not implemented.** The interfaces avoid LangGraph-shaped assumptions and the
  neutrality test enforces it, but the claim stays untested until a third backend exists.
- **`RuntimeBackend.run()` is unimplemented on both backends.** In-process execution goes
  through the generated code.
- **Claude Code tool wiring is manual.** A Python-callable tool can be named but not imported;
  `BRIDGE103` says so, and connecting it over MCP is your job.
- **The importer recovers no control flow.** By construction — a plugin contains none.
